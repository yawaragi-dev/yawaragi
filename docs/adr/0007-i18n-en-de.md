# English + German UI from day one via next-intl

Internationalisation is set up in Phase 0, before any feature work, using `next-intl`. Default locale is `en`; the second locale is `de`. All user-facing strings flow through `useTranslations` / `getTranslations` — no inline literals in JSX. Japanese kanji and romaji are preserved verbatim alongside both locales because they are part of the data, not translatable copy. A locale switcher lives in the header; `Accept-Language` provides the initial guess; user choice persists in a cookie. The PR template carries an explicit "i18n: all new strings translated to de" checkbox and components without German translations do not merge.

We chose to do this from Phase 0 rather than back-fill later because the project's primary geographies are global English-speaking sake-curious audiences and Germany / DACH, and retrofitting i18n into a component-heavy Next.js app costs disproportionately more than building with it from the start. The cost in Phase 0 is roughly an hour of setup; the cost of back-filling later is days of churn across every component plus a guaranteed regression surface.

## Consequences

- Every component ships with at least two `.json` message catalogues (`messages/en.json`, `messages/de.json`).
- A small German-fluent human reviewer pass is required before any public launch (see the pre-go-live checklist). Claude can draft the German strings but the final review must be a native or near-native speaker — literal-but-wrong translations are the most common failure mode.
- Translation is forbidden for Japanese sake names, brewery names, prefecture names, and the 6-axis vocabulary. These are preserved as kanji + romaji and rendered identically across locales.
- The forbidden-copy audit (see ADR-0006) scans both locale catalogues for promotional phrases.
