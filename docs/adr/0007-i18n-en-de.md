# English + German UI from day one via next-intl

Internationalisation is set up in Phase 0, before any feature work, using `next-intl`. Default locale is `en`; the second locale is `de`. All user-facing strings flow through `useTranslations` / `getTranslations` — no inline literals in JSX. Japanese kanji and romaji are preserved verbatim alongside both locales because they are part of the data, not translatable copy. A locale switcher lives in the header; `Accept-Language` provides the initial guess; user choice persists in a cookie. The PR template carries an explicit "i18n: all new strings translated to de" checkbox and components without German translations do not merge.

We chose to do this from Phase 0 rather than back-fill later because the project's primary geographies are global English-speaking sake-curious audiences and Germany / DACH, and retrofitting i18n into a component-heavy Next.js app costs disproportionately more than building with it from the start. The cost in Phase 0 is roughly an hour of setup; the cost of back-filling later is days of churn across every component plus a guaranteed regression surface.

## Amendment — 2026-09-30: the switcher's home moves to §15 Account

The original decision says "a locale switcher lives in the header." That was written in Phase 0, when the header was the app's nav backbone and the only chrome there was. Design v1.4 reassigns both edges: rule 11 gives the **top edge** to "where am I / go back" and the **bottom edge** to the tab bar, and §15 Account is where the design puts **Language** — a settings row with the value "English" and the sub-line "Deutsch — coming soon".

So the header switch and §15's row are the same affordance specified in two places, and #312 shipped both: the row exists, and the header switch stayed because this ADR requires it. A visitor on `/en/account` sees "Language · English" in the page and an "English · Deutsch" control in the header above it. That is not a port gap to close later; it is this ADR contradicting the design, and one of them has to move.

**The decision: the switcher's canonical home is §15's Language row. The header keeps it only until that row is a control.**

The requirement this ADR actually protects is *"a visitor can always change locale, and does not have to hunt"*. "In the header" was how we met it, not the requirement itself. What replaces it:

- **Locale choice is reachable from every app screen in at most two taps** — avatar → Account → Language. That is the same two-tap budget §15 already sets for the Impressum, and it is met by the Account entry #312 put in the header.
- **The landing keeps its own switch.** §0 specifies `EN (selected) · "DE · soon"` in the landing header, and the landing is outside the app shell with no tab bar and no avatar. `<LandingHeader />` is a separate component and is unaffected by this amendment.
- **The non-launched-locale page keeps a cross-locale path in its body.** A `de-DE` browser lands on `/de` coming-soon, which is not an app screen and has no Account entry; its "Open the English preview" link is the switch for that visitor, and #309 additionally gave that page a back arrow resolving to `/en`.

### Why not just delete the header switch now

Because §15 says the Language row is **"not tappable until DACH launch"**, and today that is correct: `LAUNCHED_LOCALES` holds only `en` (ADR-0008), so every path to `de` ends at coming-soon. A switch whose only destination is a "coming soon" page is not a language switch. Removing the header control while the row is inert would leave the app with no locale affordance at all — which is the thing this ADR exists to prevent.

So the sequencing is explicit, and the trigger is `LAUNCHED_LOCALES`, not a date:

1. **Now** — §15's Language row exists and is inert, per §15. The header keeps its switch. Both are present, and the duplication is the documented cost of the DACH launch not having happened.
2. **When `de` joins `LAUNCHED_LOCALES`** — §15's row becomes a real control in the same PR, and the header switch is removed in that PR. Not before: the row has to work on the day the header stops offering the alternative.

A reviewer who finds the duplication and "tidies" the header switch away before step 2 breaks this ADR. That is the failure this amendment is written to make visible, which is why the sequencing is here rather than in a comment.

### Consequences changed

- The sentence "A locale switcher lives in the header" is **superseded** by "a locale switcher is reachable in at most two taps from every screen; §15 Account's Language row is its canonical home, and the header carries it only while that row is inert."
- `Accept-Language` for the initial guess and the cookie for persistence are **unchanged**. This amendment is about where the control is, not how locale is resolved or stored.
- The i18n-parity requirement — every string in both catalogues, no English-only merges — is **unchanged**.
- Test consequence: specs that locate the switcher by `data-testid="locale-switcher"` in the app header are asserting step 1, not the requirement. When step 2 lands they move to the Account row rather than being deleted, so the two-tap guarantee stays pinned.

## Consequences

- Every component ships with at least two `.json` message catalogues (`messages/en.json`, `messages/de.json`).
- A small German-fluent human reviewer pass is required before any public launch (see the pre-go-live checklist). Claude can draft the German strings but the final review must be a native or near-native speaker — literal-but-wrong translations are the most common failure mode.
- Translation is forbidden for Japanese sake names, brewery names, prefecture names, and the 6-axis vocabulary. These are preserved as kanji + romaji and rendered identically across locales.
- The forbidden-copy audit (see ADR-0006) scans both locale catalogues for promotional phrases.
